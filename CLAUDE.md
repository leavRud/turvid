# Turvid — сайт-дневник походов

Личный сайт: загружаю записанный трек (GPX/KML/KMZ/GeoJSON) и фото/видео, привязываю их к точкам маршрута и «прохожу» поход заново, двигая стрелку по карте.

**Полное ТЗ — `docs/TZ.md`. Читай его перед любой задачей.** Если задача противоречит ТЗ или в ТЗ чего-то не хватает — спроси, не додумывай.

## Как работаем

- Делаем по этапам из раздела 8 ТЗ, **один этап за раз**. Не начинай следующий этап, пока я не скажу.
- В начале этапа коротко напиши план (файлы, шаги), потом делай.
- В конце этапа: `npm run typecheck`, `npm run lint`, `npm test` и `npm run build` проходят без ошибок; проверь критерий «Готово, когда» из ТЗ; сделай коммит `этап N: <что сделано>`.
- Мелкие коммиты внутри этапа приветствуются.
- Отвечай и пиши комментарии в коде на русском; имена в коде — на английском.

## Стек

- Vite + TypeScript (`strict: true`), **без UI-фреймворков** (никаких React/Vue/Svelte). DOM руками, ES-модули.
- Карта: MapLibre GL JS, подложка OpenFreeMap.
- Разбор треков: `@tmcw/togeojson`, `jszip` (KMZ). Геометрия: `@turf/turf`, `simplify-js`.
- Фото и видео: `exifr`, `heic2any`, `mp4box.js`. Часовой пояс: `tz-lookup`.
- Бэкенд: Supabase (Auth по ссылке на почту, Postgres + RLS, Storage для треков, Edge Functions `share` и `media`) через `@supabase/supabase-js`.
- Фото и видео: Cloudflare R2 (приватный бакет). Ключи R2 — только в секретах Supabase (`R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`); браузер получает подписанные ссылки от функции `media`.
- Тесты: Vitest. Линтер: ESLint + Prettier.
- Новые зависимости добавляй только если без них правда сложно, и скажи, зачем.

## Структура

```
src/
  parse/    разбор GPX, KML, KMZ, GeoJSON → общий формат точек
  track/    обработка трека: чистка, дни, расстояние, высота, остановки, упрощение, статистика (+ worker)
  map/      карта, слой трека, стрелка, маркеры точек
  player/   позиция, ползунок, магнит, нижняя полоса (профиль высоты / шкала времени)
  photos/   EXIF, HEIC, сжатие, видео-метаданные, автораскладка
  api/      всё общение с Supabase — больше нигде supabase не вызывается
  pages/    экраны: вход, список, новый поход, просмотр, статистика, публичный просмотр
  ui/       общие компоненты и стили
  types.ts  общие типы (Hike, TrackData, Point, Media)
supabase/
  migrations/  SQL-миграции (схема из раздела 3 ТЗ + RLS)
  functions/   edge function share
docs/TZ.md
test/fixtures/ эталонные треки
```

## Правила кода

- `parse/`, `track/`, `photos/placement` — **чистые функции без DOM и сети**, каждая покрыта тестами. Это ядро, тут ошибки дороже всего.
- Обработка трека идёт в Web Worker, интерфейс не должен замирать.
- Единица позиции на треке — метры от старта (`pos_m`). Всё, что «на маршруте», адресуется ею.
- Никаких `any` без комментария, почему иначе нельзя.
- Цвета и размеры — только CSS-переменные (светлая и тёмная тема).
- Вёрстка mobile-first: всё работает от ширины 360 px, кнопки и ползунок не меньше 44 px.
- Ключи и URL Supabase — только из `.env` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`), файл `.env` в `.gitignore`. Service role key никогда не попадает во фронтенд.
- Изменения схемы БД — только новыми миграциями, старые не правим.

## Эталонные данные

`test/fixtures/zepp-2days.gpx` — мой реальный трек с Amazfit T-Rex 3 Pro: 51 000 точек раз в секунду, 13,7 МБ, 17–18 октября 2026, два дня с ночным разрывом ~14 ч, ~32 км, высота уплыла с 10 до −117 м (барометр). На нём проверяются критерии раздела 4 ТЗ: 2 дня, 31–33 км, высота помечена ненадёжной, ~23 остановки от 5 минут.

Файл большой: для юнит-тестов делай из него маленькие вырезки, полный файл гоняй в отдельном медленном тесте.
